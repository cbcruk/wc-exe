# 왕복 비용 모델 — 무엇을 예산으로 삼는가

정확한 것만으로는 부족하다. wc-exe가 존재하는 이유 자체가 비용이기 때문이다 — 보안 소프트웨어의
실시간 검사가 `npm install`의 I/O를 못 쓰게 만드는 것을 우회하려고 만든 도구다. 빌드가 맞게
나오지만 느리면 그건 반쯤 실패한 것이다.

그래서 **프로토콜을 바꾸는 변경은 왕복 횟수로 심사한다.** 이 문서가 그 예산이고,
`src/daemon/daemon.integration.test.ts`의 `what one build costs`가 그것을 고정한다.

## 예산의 단위는 둘이다

| 단위               | 무엇                                | 어디서 세나                                 |
| ------------------ | ----------------------------------- | ------------------------------------------- |
| **제어 채널 왕복** | 호스트 → 페이지 `wcRunner` 호출 1회 | SSE 프레임 1개 내려가고 POST 1개 올라온다   |
| **러너 평면 요청** | 페이지 → 호스트 HTTP 요청 1회       | `/api/files`, `/api/files/raw`, `/api/dist` |

둘을 나눠 세는 이유: **제어 채널 호출 하나가 러너 평면 요청 N개로 펼쳐진다.** `mountFromServer`는
RPC 1회지만 그 뒤에 파일 수만큼의 GET이 있다. 앞의 숫자만 보면 비용이 상수처럼 보인다.

`FakeRunnerPage`가 양쪽을 다 센다 — `calls`와 `requests`. 인메모리 백엔드를 만든 부수 효과로
비용이 **주장이 아니라 검사 가능한 수치**가 되었다.

## 빌드 한 번 (데몬 경로)

제어 채널 왕복 **6회**, 그리고 프로젝트 크기와 무관하게 고정이다.

| #   | 호출                    | 단계      | 조건                               |
| --- | ----------------------- | --------- | ---------------------------------- |
| 1   | `removePaths`           | sync      | 호스트에서 사라진 경로가 있을 때만 |
| 2   | `mountFromServer`       | sync      | 바뀐 파일이 있을 때만              |
| 3   | `resolvePackageManager` | —         | 매번 (락파일이 바뀔 수 있다)       |
| 4   | `installWithCache`      | install   | `--no-install`이 아니면            |
| 5   | `removePaths`           | clearDist | 데몬 경로는 항상                   |
| 6   | `runCommand`            | build     | 항상                               |
| 7   | `uploadDist`            | upload    | 항상                               |

첫 빌드는 삭제가 없으므로 6회(1번 제외), 이후 빌드는 6~7회다. 일회성 경로(`wc-exe build`)는
`clearDist: false`라 5번이 빠지고, 컨테이너가 매번 새것이라 1번도 없다.

## 러너 평면 요청 — 여기가 실제 비용이다

- `mountFromServer` → `GET /api/files` **1회** + `GET /api/files/raw` **파일 수만큼**
- `uploadDist` → `POST /api/dist` **산출물 수만큼**

## 지켜야 할 규칙

> **핫 패스의 비용은 프로젝트 크기가 아니라 diff 크기에 비례해야 한다.**

일회성 빌드에서 전체 파일을 한 번 읽는 것은 비용이 아니라 정의다. 문제는 **같은 컨테이너에
반복해서 빌드하는 경로** — 데몬이 존재하는 이유 그 자체 — 이고, 거기서는 바뀐 것만큼만 들어야 한다.

## 알려진 위반 (미해결)

**두 번째 빌드도 파일을 전부 다시 읽는다.** 한 글자만 고쳐도 프로젝트 전체가 HTTP로 다시 넘어간다.

호스트는 무엇이 바뀌었는지 이미 알고 있다 — `diffManifests`가 계산했고, `Session.sync`는 그
plan이 비어 있지 않아서 mount를 부른다. 그런데 `mountFromServer`는 **인자를 받지 않는다.**
페이지는 매니페스트를 다시 받고 그 안의 모든 파일을 다시 받는다.

측정된 값 (파일 4개 프로젝트, 파일 하나 수정, 빌드 2회):

```
requests = { manifest: 2, files: 8, artifacts: 2 }
                          ^^^^^^^^
                          4 + 4. 두 번째 빌드에서 바뀐 파일은 하나였다.
```

고치려면 페이지에 "이 경로들만 가져와라"를 말할 방법이 필요하고, 그건 러너 번들의 API 변경이다.
그 전까지 이 숫자가 정직한 값이고, **테스트에 그대로 박아 뒀다** — 고쳐지면 숫자가 줄어들면서
테스트가 깨진다. 줄어드는 방향으로 깨지는 것이 목적이다.

`src/daemon/session.ts`의 sync 주석에 "afterwards it re-reads files the host says changed"라고
적혀 있는데, **사실이 아니다.** 호스트는 무엇이 바뀌었는지 말하지 않는다. 주석이 틀렸다는 것을
이 문서가 알아냈다.

## 이 문서가 재지 않는 것

벽시계 시간이다. 부팅 몇 초, install 몇 초, 캐시 HIT/MISS 이득 — 그건 `bench/`와
`docs/persistent-runner.md`가 담당하고, 실제 머신에서만 의미가 있다.

여기는 **셀 수 있는 것만** 다룬다. 왕복은 코드에서 정적으로 세지고, 기계나 네트워크에 의존하지
않으며, 따라서 이 샌드박스에서도 회귀를 잡을 수 있다. 실측 없이 판단할 수 있는 유일한 비용이다.

## 바꿀 때

1. 왕복이 늘어나는가? 늘어난다면 왜 그만한 값어치가 있는지 여기에 적는다.
2. 늘어난 비용이 프로젝트 크기에 비례하는가? 그렇다면 핫 패스에 두지 않는다.
3. `what one build costs` 테스트의 숫자를 같이 고친다. **`toBeLessThan`으로 바꾸지 않는다** —
   상한만 있는 예산은 한 번에 하나씩 올라가면서 아무 의미도 없어진다.
