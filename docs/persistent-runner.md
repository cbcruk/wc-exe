# 상주 러너(persistent runner) 설계

> `docs/virtual-filesystem.md` §10의 후속. 캐시가 install을 11.66s → 0.30s로 줄인 뒤 **부팅이 지배적 비용**이 됐다. 이 문서는 그 부팅을 반복 비용에서 제거하기 위한 설계다.
>
> **범위.** 목적은 컨테이너 안에서 빌드를 돌리고 **산출물을 꺼내오는 것**이다. 범용 개발 머신을 만드는 게 아니다 — 그래서 §2.2에서 `git`이 없다는 사실은 문제가 되지 않는다(형상 관리는 호스트 쪽 일이다). 이 경계가 어떤 부재를 감수할 수 있고 어떤 것을 감수할 수 없는지를 가른다.
>
> **상태.** Phase 0~2 구현 완료. 데몬이 동작하고 `wc-exe build --daemon`으로 쓸 수 있다. 측정 결과와 남은 위험은 §12를 볼 것.
>
> **§1은 재측정된 값으로 교체했다.** 원래 수치는 OPFS 캐시 HIT가 실행 권한 없는 `node_modules`를 복원하던 시절(§12.1)에 잰 것이라 무효였다. §13에 재측정 결과와, 그 과정에서 나온 버그 세 개가 있다.

## 1. 왜 지금 이것인가

부팅이 매 실행 반복되는 고정 비용이고, install을 캐시로 줄이고 나면 남은 가장 큰 덩어리다. **엔진 교체(§7에서 35× 느림으로 탈락)보다 훨씬 싼 개선**이기도 하다.

부수 효과도 있다: 컨테이너가 살아 있으면 `node_modules`가 메모리에 그대로 남아, OPFS에서 복원하는 시간조차 사라진다.

**재측정 결과(macOS, `sample-vite-app`, CLI 종단간):**

| 경로                       | 시간      |
| -------------------------- | --------- |
| 콜드 (캐시·부팅 모두 없음) | 18.1s     |
| 일회성 `--cache` warm      | 4.22s     |
| **데몬 warm**              | **1.98s** |
| 데몬 첫 실행(부팅 포함)    | 4.16s     |

**빌드당 2.23s 절약(53%), 두 번째 빌드부터 이득.**

> ⚠️ 이건 **작은 픽스처** 기준이다. 절약분의 상한은 부팅 시간이므로 **빌드 자체가 무거운 프로젝트일수록 상대 이득은 줄어든다.** 실제 대상 프로젝트에서 `node bench/daemon.mjs <프로젝트>`로 직접 재고 판단할 것. 절약이 0 이하로 나오면 속도를 근거로 한 정당화는 무너지지만, 그게 이 작업 전체를 기각하지는 않는다 — §8이 적었듯 대화형 세션에서는 상주화가 최적화가 아니라 전제다.

## 2. 확인된 제약 — 실측

### 2.1 페이지당 WebContainer 하나

`@webcontainer/api` 타입에 명시돼 있다:

> "Only a single instance of WebContainer can be booted concurrently (see `teardown`)."

여기서 구조가 강제된다:

- **세션 = 페이지 = 프로젝트.** 한 페이지는 프로젝트 하나만 담을 수 있다.
- **동시에 여러 프로젝트** → 페이지를 여러 개. 각각 부팅 비용(~5.4s)을 한 번씩 내지만, 그 다음부터는 프로젝트별로 상각된다.
- **완전 초기화** = `teardown()` 후 재부팅 = 부팅 비용을 다시 지불. 즉 "리셋은 공짜가 아니다"가 설계 전제다.
- `coep`는 **최초 부팅 때 고정**되고 재부팅으로 못 바꾼다(타입 문서). 데몬이 이 값을 프로세스 수명 동안 일관되게 유지해야 한다.
- 선택적 정리는 `fs.rm(path, {recursive})`으로 teardown 없이 가능하다.

### 2.2 런타임 실측 — `poc/webcontainer-shell-probe`

"살아 있는 컨테이너에 셸처럼 붙는다"가 가능한지는 문서가 아니라 프로브로 확인했다. macOS / `@webcontainer/api` 1.6.4, **17 pass · 1 fail**, 부팅 3.6s.

**세션 모델은 성립한다.** `spawn`이 붙여주는 것은 진짜 의사터미널이다 — stdin으로 친 명령이 실제로 실행되고, 입력이 에코되고, ANSI 이스케이프가 오고, `cd`가 입력 사이에 유지되고, Ctrl-C가 포그라운드만 죽이고 셸은 살아남는다. `terminal: {cols,rows}`가 프로세스가 보는 폭에 반영되고 `resize()`가 실행 중 프로세스에 이벤트로 도달한다. `cwd`/`env`도 반영되고 프로세스 동시 실행도 된다.

셸은 **`jsh` 하나**다. `sh`·`bash`·`zsh`는 전부 jsh 심볼릭 링크이고 `ash`·`dash`는 없다.

**`fs` API는 시스템 파일시스템을 못 본다.** 절대 경로가 workdir 기준으로 해석돼 `fs.readdir('/bin')`이 `/home/<workdir>/bin`에서 ENOENT를 낸다. 바이너리는 존재하지만 `fs`에는 안 보인다 — 런타임을 조사하려면 **셸을 통해야 한다.**

**설치된 것은 46개.** node/npm/npx/pnpm/yarn/python3/curl/jq와 기본 파일 도구(ls, cat, cp, mv, rm, mkdir, chmod, ln, head, sort, tail, touch, xxd, ps, kill).

없는 것 중 이 프로젝트에 실제로 걸리는 것만 추리면:

| 없는 것                      | 영향                                                                                                           |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `git`                        | **무관.** 산출물만 꺼내오면 되고 형상 관리는 호스트 쪽 일이다                                                  |
| `vi`                         | 무관. 헤드리스다                                                                                               |
| `grep`, `sed`, `tar`, `wget` | **빌드 성공률에 걸린다.** `package.json` 스크립트가 셸로 빠지면 깨질 수 있다. 호스트로 옮길 수 없는 제약       |
| `gcc`                        | 네이티브 모듈(node-gyp) 빌드 불가. 단 WebContainer가 원래 네이티브 애드온을 지원하지 않으므로 새 제약은 아니다 |

즉 이건 "리눅스 박스에 SSH"가 아니라 **"Node 샌드박스에 SSH"**다. 빌드 구동과 산출물 회수라는 이 프로젝트의 목적에는 충분하다.

### 2.3 jsh는 입력을 몰아 쓰면 job control이 죽는다 — 설계에 직접 걸린다

앞 명령이 끝나기 전에 다음 명령 줄을 쓰면 jsh가 내부 에러를 던진다:

```
jsh: Cannot read properties of undefined (reading 'exitCode')
```

**그 뒤로 셸은 멀쩡해 보이는데 job control만 조용히 죽는다.** 명령은 계속 실행되고 출력도 나오는데, Ctrl-C에 반응할 포그라운드 잡이 없다. A/B로 확정했다 — 쓰기를 직렬화(프롬프트를 기다린 뒤 다음 줄)하면 내부 에러가 사라지고 정상 동작한다.

그래서 프로브는 갓 띄운 셸(`pty.sigint`)과 명령을 25개 처리한 셸(`pty.sigint_aged`)을 **분리해서** 보고한다. 실패가 셸 문제인지 세션 수명 문제인지 구분되도록.

**데몬은 한 세션을 오래 붙들고 여러 요청이 공유하므로, 세션당 쓰기 직렬화가 선택이 아니라 요구사항이다.** 안 지키면 "빌드는 계속 되는데 취소만 안 먹는" 상태로 조용히 넘어간다 — §6이 경계하는 거짓 성공과 정확히 같은 부류다.

#### 직렬화 대상은 "명령 줄"이지 "입력 전부"가 아니다

이 구분을 처음에 틀렸다가 통합 테스트에서 잡았다. 기록해 둘 가치가 있다.

jsh를 깨뜨리는 것은 **앞 명령이 끝나기 전에 쓰인 명령 줄**이다. Ctrl-C(0x03)는 여기 해당하지 않는다 — 오히려 **실행 중인 명령에만 의미가 있으므로 큐를 타면 안 된다.** 큐는 앞 명령이 끝날 때까지 다음 쓰기를 붙잡아 두는 장치이므로, 인터럽트를 큐에 넣으면 "죽이려던 대상이 이미 끝난 뒤에 도착"하는 것이 보장된다. 실제 터미널이 제어 문자를 대역 외로 보내는 이유와 같다.

관련해서 하나 더: **유휴 프롬프트에서의 Ctrl-C는 고장이 아니다.** 처음 구현은 `^C` 에코가 안 오면 세션을 broken으로 표시했는데, 실행 중인 명령이 없으면 jsh는 아무것도 에코하지 않는다(실제 터미널도 그렇다). 그대로 뒀다면 멀쩡한 세션을 계속 폐기하고 데몬이 매번 부팅 비용을 다시 냈을 것이다.

정리하면 `ShellSession`(`src/runner/src/runtime/shell-session.ts`)의 규칙은:

| 입력                 | 직렬화      | 이유                                   |
| -------------------- | ----------- | -------------------------------------- |
| 명령 줄 (`exec`)     | **큐**      | 이르게 쓰면 jsh의 job control이 죽는다 |
| Ctrl-C (`interrupt`) | **대역 외** | 큐를 타면 항상 늦게 도착한다           |

인터럽트된 `exec`는 완료 마커를 영영 못 받으므로(셸이 명령 리스트의 나머지를 버린다) 타임아웃까지 매달리지 않고 `interrupted: true`로 끝난다.

#### 깨진 상태를 무엇으로 감지할 것인가 — 실측으로 골랐다

처음 감지 근거는 jsh가 찍는 에러 문자열 하나였다. 문구가 바뀌면 조용히 못 잡는다는 게 §10의 미해결 항목이었다. 후보 신호들을 **건강한 셸과 일부러 깨뜨린 셸에 나란히 걸어서** 실제로 구별되는지 쟀다:

| 후보 신호                        | 건강 | 깨짐 | 쓸 수 있나                             |
| -------------------------------- | ---- | ---- | -------------------------------------- |
| 명령이 실행되는가                | ✅   | ✅   | **아니오**                             |
| 실패 명령 뒤 `$?`                | `2`  | `2`  | **아니오** — 종료 상태 추적은 멀쩡하다 |
| 성공 명령 뒤 `$?`                | `0`  | `0`  | **아니오**                             |
| `^C` 에코                        | ✅   | ❌   | 예                                     |
| **Ctrl-C 뒤 다음 명령이 도는가** | ✅   | ❌   | **예 — 문자열에 의존하지 않음**        |
| jsh 에러 줄                      | 없음 | 있음 | 예, 단 문자열 의존                     |

중요한 부정 결과: **`$?`는 깨진 뒤에도 정확하다.** 그래서 "종료 상태가 이상해지면 감지" 같은 값싼 검사는 성립하지 않는다. 다시 시도하지 말 것.

그래서 3층으로 나눴다:

1. **`verifyJobControl()` — 권위 있는 검사, 문자열 무의존.** 끝나지 않는 명령을 띄우고 인터럽트한 뒤 **그 다음 명령이 도는지**를 요구한다. 깨진 셸은 죽이지 못한 프로세스가 터미널을 계속 붙들고 있어서 여기서 걸린다. 몇 초 걸리므로 세션을 넘겨줄 때·유휴에서 복귀할 때 돌린다(막아주는 재부팅이 ~5s이므로 충분히 싸다).
2. **`exec`의 수동 검증 — 공짜.** 인터럽트를 *보낸 것*은 인터럽트가 *먹힌 것*이 아니다. 실제로 효과가 보일 때까지 기다리고, 안 보이면 broken으로 표시한다. 이게 없으면 여전히 돌고 있는 명령을 "취소됨"으로 보고하게 된다 — 처음 구현이 실제로 그랬다.
3. **에러 문자열 — 조기 경보.** 깨지는 순간 바로 뜨지만 문구 의존이다.

**문자열 휴리스틱이 이론상 취약한 게 아니라 이미 실제로 놓친다.** 통합 테스트에서 공개 API로 셸을 손상시켰더니(`shellExec`에 개행을 끼워 넣으면 큐를 우회해 두 줄이 한 번에 쓰인다) `brokenReason`은 `null`인데 `verifyJobControl()`은 `false`였다. 게다가 jsh가 에러를 찍을지 말지가 **실행마다 다르다.** 그래서 통합 테스트는 "어느 신호가 잡았는가"가 아니라 **"손상된 세션이 절대 healthy로 보고되지 않는다"**를 검증한다.

## 3. 구조

```
wc-exe build            (짧게 살고 죽는 CLI)
   │  HTTP + 토큰, 로그는 스트리밍
   ▼
데몬 (오래 사는 프로세스)
   ├─ Hono 서버        127.0.0.1:5199 고정 (OPFS origin 안정성)
   ├─ Chromium         영속 프로파일 (~/.cache/wc-exe/chrome-profile)
   └─ 세션 N개 = 페이지 N개
        └─ 부팅된 WebContainer + 마운트된 프로젝트 + 살아있는 node_modules
```

포트 고정과 영속 프로파일은 **이미 `--cache`가 요구하던 것**이라(`src/core/cache.ts`) 새로 도입되는 제약이 아니다. 데몬은 그걸 자연스럽게 흡수한다.

## 4. 브릿지를 왜 고쳐야 하는가

지금 브릿지(`src/core/browser.ts`)는 **일회성**이다: 연산마다 `page.evaluate`로 `window.wcRunner.*`를 부르고, 로그는 puppeteer가 `console.log`를 긁어 stdout에 찍는다. 같은 프로세스가 페이지를 들고 있으니 이게 성립한다.

데몬에선 **CLI와 페이지를 들고 있는 프로세스가 다르다.** 그래서 브릿지가 이렇게 바뀌어야 한다:

|      | 지금                           | 상주 후                                |
| ---- | ------------------------------ | -------------------------------------- |
| 호출 | `page.evaluate` 일회성         | 세션 스코프 요청/응답                  |
| 로그 | puppeteer가 console 스크레이핑 | CLI로 **스트리밍**(SSE 또는 chunked)   |
| 취소 | 프로세스 죽이면 끝             | 명시적 취소 + 서버측 정리              |
| 상태 | 없음(매번 새 컨테이너)         | 세션이 상태를 **가진다** ← 위험의 근원 |

즉 이 작업의 본체는 데몬 껍데기가 아니라 **브릿지를 수명 있는 프로토콜로 올리는 것**이다.

### 지금 브릿지가 버리고 있는 것

§2.2에서 확인했듯 `spawn`은 완전한 의사터미널을 준다. 그런데 현재 `Runtime`은 그중 **종료 코드 하나만** 통과시킨다:

| WebContainer가 주는 것          | 현재 `Runtime` / `WCBrowser`                      |
| ------------------------------- | ------------------------------------------------- |
| `input` (PTY stdin)             | **없음** — `spawn(command, args)`이 받지도 않는다 |
| `output` 스트림                 | `console.log`로 흘리고 puppeteer가 긁는다         |
| `kill()`                        | **없음**                                          |
| `resize()`                      | **없음**                                          |
| `cwd` / `env` / `terminal` 옵션 | **없음**                                          |
| `exit`                          | 유일하게 살아남는다                               |

**완료.** `RuntimeProcess`는 `{ input, output, exit, kill, resize }`이고 `spawn`이 `SpawnOptions`를 받는다. `WebContainerRuntime`은 여전히 passthrough다 — `WebContainerProcess`가 이미 정확히 이 모양이었다. 백엔드 중립성도 유지된다(PTY는 WebContainer 고유가 아니다).

그 위에 얹힌 것:

- `runCommand`가 출력을 캡처해 `{ exitCode, output, truncated, droppedChars }`를 돌려준다. 상한을 넘으면 **꼬리를 남기고**(실패는 끝에서 보고되므로) 잘렸다는 사실을 반드시 알린다.
- 취소: 호출자가 정한 handle로 `killCommand` / `resizeCommand`. 타임아웃은 이제 **명령을 죽이고** 나서 던진다(예전엔 페이지 안에서 계속 돌았다).
- `ShellSession` + `openShell`/`shellExec`/`shellInterrupt`/`shellResize`/`closeShell`. 출력은 `page.exposeFunction`으로 **푸시**된다(폴링 아님).
- 사용자에게 보이는 이득: 빌드 실패 시 종료 코드만이 아니라 **실패 출력**이 나온다.

**두 가지는 여전히 데몬 몫이다.** CLI↔데몬 사이의 로그 스트리밍과 취소 전달. 지금은 CLI가 페이지를 직접 들고 있어서 in-process로 끝난다.

### 제어 평면 / 러너 평면 분리

한 서버가 두 종류의 클라이언트를 받는다. 섞으면 안 된다.

- **러너 평면** — 페이지가 부른다: `/api/files`, `/api/files/raw`, `/api/dist`. Origin이 `http://localhost:5199`.
- **제어 평면** — CLI가 부른다: `/control/*`. 토큰 필요, Origin 헤더가 **있으면 거부**.

## 5. 보안 — 이게 새로 생기는 위험이다

지금 서버는 **빌드 중에만, 랜덤 포트로** 뜬다. 데몬은 **고정 포트로 항상 떠 있고 빌드를 실행**한다. 노출 성격이 다르다.

사용자가 방문한 아무 웹페이지나 `http://localhost:5199/control/build`로 POST할 수 있다는 뜻이다. 최소한 다음이 필요하다:

1. **127.0.0.1에만 바인드** (0.0.0.0 금지).
2. **베어러 토큰** — `~/.cache/wc-exe/daemon.json`에 `0600`으로 저장. 제어 평면 필수.
3. **`Origin` 헤더가 있는 제어 평면 요청은 거부** — 브라우저는 크로스오리진 POST에 Origin을 붙이고, 정상 CLI는 안 붙인다. 러너 평면은 반대로 자기 origin만 허용.
4. 데몬이 **프로젝트 경로를 검증** — CLI가 임의 경로를 넘겨 빌드시키지 못하게. (제어 평면이 이미 토큰으로 막히지만 방어 계층 하나 더.)

## 6. 진짜 어려운 부분 — 헐메틱성

지금 모델은 **매 빌드가 새 컨테이너에서 시작**한다. 상주화는 그 성질을 속도와 맞바꾼다. 이 프로젝트는 **이미 이 부류의 버그에 물린 적이 있다** — 빈 디렉터리를 캐시 HIT으로 보고해 빌드가 `vite: command not found`로 죽었던 건(§5) 상태를 잘못 신뢰한 결과였다.

그래서 무엇이 남고 무엇이 지워지는지를 **명시적으로 정의**해야 한다.

| 대상                  | 요청 간                    | 이유                                                  |
| --------------------- | -------------------------- | ----------------------------------------------------- |
| 소스 파일             | **매번 동기화**            | 호스트가 진실의 원천                                  |
| `node_modules`        | **유지**                   | 이 작업의 이득 자체                                   |
| `dist/`               | **매번 삭제**              | 이전 산출물이 섞이면 안 됨                            |
| `.npm-cache`          | 유지                       | 타르볼 캐시                                           |
| 셸의 `cwd`·환경 변수  | **요청마다 초기화**        | 이전 요청의 `cd`가 남으면 상대 경로가 조용히 어긋난다 |
| 그 외 컨테이너 잔여물 | 매니페스트 차집합으로 삭제 | 아래 참조                                             |

여기에 §2.3의 요구사항이 하나 더 붙는다: **세션당 쓰기를 직렬화하고 프롬프트를 기다린다.** 상태가 남는 것뿐 아니라 셸 자체가 망가지는 것도 막아야 한다.

### 삭제 전파 — 놓치기 쉬운 함정

`mount()`는 **추가/덮어쓰기만** 한다. 호스트에서 `src/old.ts`를 지워도 컨테이너엔 남고, 빌드가 그걸 계속 참조할 수 있다. 그러면 **호스트에 없는 파일로 빌드가 성공**하는, 가장 나쁜 종류의 거짓 성공이 된다.

따라서 동기화는 덮어쓰기가 아니라 **매니페스트 차이 계산**이어야 한다:

1. 호스트 매니페스트(경로 + mtime/해시) 수집
2. 세션이 기억하는 직전 매니페스트와 비교
3. 추가/변경 → `mount` 또는 `writeFile`
4. **삭제된 경로 → `fs.rm`**
5. 새 매니페스트를 세션에 저장

### 리셋 트리거 (teardown + 재부팅)

- lockfile 변경 → 사실은 캐시 키가 이미 처리하므로 리셋까지는 불필요. install만 다시.
- **wc-exe 버전 변경** → 러너 번들이 바뀌었으므로 리셋 필수
- `--fresh` 명시
- 세션이 오류 상태(이전 요청이 예외로 끝남)
- 유휴 만료

## 7. 수명 주기

- **자동 시작** — 첫 CLI 호출이 데몬을 detached로 띄운다. 사용자가 따로 켤 필요 없음.
- **디스커버리** — `~/.cache/wc-exe/daemon.json`에 `{pid, port, token, version, startedAt}`.
- **헬스체크** — `GET /control/health` → 버전·업타임·세션 목록.
- **버전 불일치** — CLI가 자기 버전과 데몬 버전을 비교해 다르면 **죽이고 재시작**. 이게 없으면 업그레이드 후에도 낡은 러너가 계속 돈다(실제로 겪기 쉬운 함정).
- **유휴 종료** — 기본 10분 무요청 시 종료. 메모리를 무한정 붙들지 않기 위함.
- **크래시 복구** — CLI가 연결 실패하면 stale `daemon.json`을 지우고 재시작.
- **수동 제어** — `wc-exe daemon status|stop|restart`.

## 8. 단계별 진행 — 각 단계가 독립적으로 값을 낸다

**Phase 0 — 전제 검증 (측정) — 하네스 준비됨, 측정은 로컬에서**
실제 대상 프로젝트에서 `bench/webcontainer.mjs`로 boot/mount/install/build 비중을 잰다. 부팅이 실제로 지배적인지 확인.

> **이 게이트의 의미가 바뀌었다.** 원래 STOP 조건은 "부팅 비중이 작으면 중단"이었다. 그건 상주화를 **최적화**로 볼 때의 이야기다. §2.2에서 대화형 세션이 실제로 성립하는 것이 확인된 이상, 명령마다 재부팅하는 셸은 존재할 수 없으므로 **셸을 원한다면 상주화는 전제이지 최적화가 아니다.**
>
> 따라서 Phase 0의 STOP은 "데몬을 **속도 개선으로서** 정당화할 수 있는가"에만 답한다. 부팅 비중이 작게 나와도 셸 방향은 계속 유효하고, 다만 그때는 **속도가 아니라 대화형 접근이 근거**라는 것을 명시하고 가야 한다.

기존 하네스는 **cold만** 잴 수 있었다 — 매 실행 새 프로파일에 맨 `npm install`. 그 수치로는 이 질문에 답할 수 없다(설계의 전제가 warm이다). 그래서 `--cache` 모드를 추가했다:

- 고정 포트 + 영속 프로파일 + `installWithCache` → **1회차는 캐시를 심고 `warmAverage`에서 제외**, 2회차부터가 측정값
- 캐시는 임시 디렉터리에 격리 — 사용자의 실제 `~/.cache/wc-exe`를 건드리지 않는다
- warm 실행에서 워밍이 실패하면(캐시 MISS 보고) **경고를 찍는다**. 조용히 cold를 warm이라 부르는 게 가장 위험한 실패다
- 단계별 비중과 3분할을 출력: **상각 가능(boot+install) / 동기화로 대체(mount) / 불가피(build)**
- 마지막에 **GO / STOP** 판정. 부팅이 warm 전체의 30% 이상이면 GO

판정 산술은 `bench/report.mjs`에 분리돼 있고 단위 테스트가 붙어 있다(`bench/webcontainer.test.mjs`). 여기서 부호가 틀리면 설계 전체가 잘못된 방향으로 간다 — 그래서 **일부러 깨뜨려 테스트가 실패하는 것까지 확인**했다(§9-4).

> 이 샌드박스에서는 WebContainer가 부팅되지 않으므로(StackBlitz 런타임 호스트 403) **실측은 로컬에서** 해야 한다. 하네스는 서버 기동·캐시 디렉터리·포트 고정·Chrome 기동·페이지 로드까지 통과하고 부팅 지점에서 멈추는 것을 확인했다.

**Phase 1 — 브릿지를 세션 프로토콜로 (데몬 없음) — 삭제 전파 완료**
`wcRunner`를 세션 개념 위로 올리고, 로그 스트리밍과 매니페스트 차이 동기화를 도입한다. 동작은 지금과 동일하게 유지(여전히 한 번 쓰고 버림). **위험이 낮고 그 자체로 유용**하며, 삭제 전파는 지금 모델에서도 옳은 개선이다.

**완료:**

- `listProjectManifest` / `diffManifests` (`src/core/file-sync.ts`) — 순수 함수, 8개 테스트. 삭제 루프를 지워보고 3개가 실제로 실패하는 것까지 확인했다.
- `Runtime.rm()` → `WebContainerRuntime` 구현 → `wcRunner.removePaths()` → `WCBrowser.removePaths()`
- **`wc-exe dev`의 실제 버그 수정.** 감시자가 `unlink`/`unlinkDir`을 아예 무시하고 있었다 — 호스트에서 지운 파일이 런타임에 남아 dev 서버가 계속 그걸 물고 있었다. 설계가 예측한 함정(§6)이 이미 현실이었던 셈이다.

**보류(데몬 없이는 검증 불가):** 세션 프로토콜과 로그 스트리밍. 지금 모델은 CLI가 페이지를 직접 들고 있어서 둘 다 이득 없이 표면적만 넓힌다. Phase 2에서 데몬과 함께 도입한다.

**알려진 별개 결함(이 단계 범위 밖):** `dev.ts`는 감시 대상 파일을 `fs.readFile(filePath, 'utf-8')`로 읽어 런타임에 문자열로 쓴다. dev 세션 중에 추가·변경된 **바이너리 파일(이미지 등)은 깨진다.** `WCBrowser.writeFile`이 문자열만 받는 것이 원인이라 시그니처 변경이 필요하다.

## 9. 어떻게 "맞다"고 증명할 것인가

속도만 재면 안 된다. 이 변경의 위험은 **틀린 산출물**이므로:

1. **바이트 동일성**: 같은 프로젝트를 (a) 일회성 (b) 데몬 재사용 두 경로로 빌드해 `dist/`를 바이트 비교. **다르면 버그.**
2. **삭제 전파**: 파일을 지우고 재빌드 → 컨테이너에서도 사라지고 빌드가 그걸 참조하지 않는지.
3. **반복 안정성**: 같은 세션에서 N회 연속 빌드 → 매번 동일 산출물(누적 오염 없음).
4. **세션 수명 후 job control**: N회 빌드를 돌린 세션에서 **취소가 여전히 동작하는지.** `poc/webcontainer-shell-probe`의 `pty.sigint_aged`가 그대로 이 검사다 — 이미 한 번 물린 실패 모드이므로 회귀 검사로 남긴다.
5. **검사의 실효성**: 위 검사들이 **일부러 깨뜨렸을 때 실패하는지** 확인. (§10 방법론 — 통과만 보면 검사가 비어 있어도 모른다.)

4번이 목록에 있는 이유: 프로브의 첫 실행이 이 실패를 "Ctrl-C가 원래 안 되는 것"으로 잘못 보고했다. 전체 transcript를 찍어보고서야 jsh 내부 에러가 원인이라는 게 드러났다. **관측을 안 남기면 원인과 증상을 구별할 수 없다** — 데몬의 취소 경로에도 같은 수준의 진단 출력이 필요하다.

## 10. 아직 모르는 것 (측정으로 답할 것)

- 대형 프로젝트에서 **매니페스트 차이 동기화 비용**. 이게 부팅 절약분을 갉아먹으면 이득이 준다.
- 오래 산 WebContainer가 **빌드 반복 시 메모리 누수**를 내는가. 유휴 종료가 완화책이지만 한계 확인 필요.
- **teardown + 재부팅 vs 새 페이지** 중 리셋이 어느 쪽이 싼가.
- 페이지(=세션) 여러 개를 동시에 띄웠을 때 Chromium 메모리 상한.
- **jsh job control이 깨지는 다른 트리거가 있는가.** "앞 명령이 끝나기 전에 다음 줄을 쓰면"은 확인됐고 직렬화로 막았다. 감지는 §2.3에서 문자열 의존을 벗어났지만(`verifyJobControl`), **트리거 목록 자체는 여전히 미완**이다. 다른 경로로도 깨진다면 데몬은 `verifyJobControl`을 얼마나 자주 돌려야 하는가 — 세션 넘겨줄 때마다? 주기적으로? 빈도를 정하려면 트리거를 더 알아야 한다.
- **`verifyJobControl`의 비용.** 몇 초라고만 알고 정확히 재지 않았다. 세션 체크아웃마다 돌린다면 상각 이득에서 빠지는 몫이므로 §11 수치에 반영해야 한다.
- 빌드 스크립트가 `grep`/`sed`를 셸로 호출하는 실제 프로젝트의 비율. 흔하면 §2.2의 부재가 이론이 아니라 실제 실패가 된다.

## 11. 기대 이득 (미검증)

warm 실행이 `5.4(부팅) + 0.3(install) + 1.6(build) ≈ 7.3s`에서 **`동기화 + 1.6(build) ≈ 2s 내외`**로 줄어드는 것이 목표다. 부팅과 캐시 복원이 모두 빠지기 때문이다.

**단, 이 수치는 아직 측정된 적 없다.** Phase 0과 Phase 3의 실측이 나오기 전까지는 가설로만 다룰 것.

## 12. Phase 2 결과 — 데몬 구현과 실측

`wc-exe build --daemon`으로 쓴다. 기본은 여전히 꺼져 있다. `wc-exe daemon status|stop|restart`로 관리한다.

### 12.1 구현하다가 발견한 것 — OPFS 캐시 HIT가 깨져 있었다

**이건 데몬이 만든 버그가 아니라 원래 있던 버그다.** 데몬은 매 빌드가 캐시 HIT 경로를 타므로 곧바로 드러났을 뿐이고, 일회성 `--cache`도 **두 번째 실행부터 똑같이 깨진다**(확인함).

증상 연쇄가 고약하다:

1. OPFS 스냅샷 왕복이 **실행 권한을 보존하지 않는다.** 복원된 `node_modules/.bin`의 파일들이 실행 불가가 된다.
2. `npm run build`가 `jsh: spawn vite EACCES`를 찍고 **종료 코드 0으로 끝난다.**
3. 그래서 "Build completed"가 찍히고, 산출물은 하나도 없다.
4. 첫 이상 신호는 한참 뒤 업로드 단계의 `ENOENT: scandir '/dist'`다.

즉 **캐시가 붙은 모든 빌드가 조용히 아무것도 만들지 않고 있었다.** §1의 "install 0.30s"는 성공한 복원이 아니라 이 상태를 잰 값이다.

고친 것 두 가지:

- 복원 직후 `chmod -R +x node_modules/.bin` (심볼릭 링크를 따라가므로 실제 파일에 적용된다).
- `uploadDist`가 산출물 디렉터리 부재를 **문장으로** 보고한다 — "빌드가 성공했다고 보고했지만 산출물이 없다. 도구가 실행되지 못해도 종료 코드 0이 나올 수 있다." 원인 불명의 ENOENT 대신.

### 12.2 실측 (macOS, sample-vite-app)

| 경로                      | 시간           |
| ------------------------- | -------------- |
| 일회성 `--cache` warm     | 4.2 ~ 5.1s     |
| **데몬 warm (정상 상태)** | **2.0 ~ 2.2s** |
| 데몬 cold (부팅 포함)     | 18.4s          |

**약 2배, 빌드당 ~2.2s 절약.** §11이 가설로 적었던 "7.3s → 2s"와는 다르다 — 이 머신·이 프로젝트에서는 일회성 warm이 애초에 4.2s였다. 절약분의 상한은 부팅 시간이므로, **빌드 자체가 큰 프로젝트일수록 상대 이득은 줄어든다.** 실제 대상 프로젝트에서 다시 재야 한다.

### 12.3 검증

**`test/integration/daemon-parity.mjs` — 14개 통과.** §9가 첫 번째로 요구한 것: 일회성과 데몬의 `dist/`를 **바이트 비교**한다. cold·warm 모두 동일하다.

삭제 전파 검사는 **처음에 이빨이 없었다.** 파일을 지우면서 import도 같이 지웠더니, 컨테이너에 남은 사본이 트리 셰이킹으로 사라져 번들이 어느 쪽이든 같았다 — 삭제 전파를 통째로 들어내도 통과했다. **import를 남긴 채** 파일만 지우도록 고쳤다: 이제 빌드가 **반드시 실패**해야 하고, 성공하면 그게 바로 "호스트에 없는 소스로 빌드가 됐다"는 증거다. 고친 뒤 다시 들어내 보니 정확히 그 실패가 나왔다.

**`test/integration/daemon-security.mjs` — 13개 통과.** §5의 주장들을 조립된 데몬에 대고 확인한다: `daemon.json`이 `0600`, 토큰 없음/틀림 → 401, 유효한 토큰이라도 `Origin`이 붙으면 → 403, 외부 인터페이스에서 접속 불가, 없는 경로·파일·빈 문자열 → 400, 모르는 세션 → 404.

**단위 테스트** `src/daemon/auth.test.ts` 11개는 가드를 격리해서 검증한다(상수 시간 비교, `Bearer` 파싱, Origin 거부).

### 12.4 검증되지 않은 것 — 통과를 과신하지 말 것

- **빌드 간 `dist` 초기화.** 코드에는 있지만 **이빨이 없다.** 들어내도 parity 테스트가 통과한다 — vite가 자기 outDir를 비우기 때문에 차이가 가려진다. outDir를 안 비우는 도구를 위해 남겨뒀을 뿐, 동작한다는 증거는 없다.
- ~~**동시 세션.**~~ → §12.5에서 해결했다.
- **유휴 종료·버전 불일치 재시작**은 코드로만 있고 실측하지 않았다.
- §10의 미해결 항목(jsh job control 트리거 목록, `verifyJobControl` 비용)은 그대로다.

### 12.5 동시 세션 — 예상보다 나빴고, 고쳤다

§12.4에 "여러 프로젝트를 동시에 열면 거부될 가능성이 높다"고 적어뒀던 항목이다. 실제로 재보니 **가능성이 아니라 확정이었고, 범위도 더 넓었다.**

```
Failed to create .../chrome-profile/SingletonLock: File exists (17)
Failed to create a ProcessSingleton for your profile directory.
Aborting now to avoid profile corruption.
```

Chrome은 **프로파일 디렉터리당 프로세스 하나**만 허용하고, 아니면 프로파일 손상을 피하려고 아예 시작을 거부한다. 세션마다 브라우저를 띄우던 구조는 이 벽에 정면으로 부딪힌다.

**"동시"만의 문제가 아니었다.** 두 번째 프로젝트는 **순차 실행에서도** 실패했다 — 첫 세션이 아직 열려 있다는 것만으로 충분했다. 즉 데몬은 프로젝트를 둘 이상 건드리는 모든 작업 흐름에서 망가져 있었고, 이건 §3이 처음부터 약속한 "세션 N개 = 페이지 N개"가 성립하지 않았다는 뜻이다.

고친 구조:

- `src/core/chrome.ts`가 Chrome 탐색·기동을 담당한다. `WCBrowser`와 데몬이 같은 코드를 쓰므로 인자나 경로 규칙이 갈라질 수 없다.
- `WCBrowser`가 **이미 떠 있는 브라우저를 받아** 그 위에 페이지만 연다. 이때 `close()`는 **자기 페이지만** 닫는다 — 브라우저는 소유자의 것이다.
- 데몬이 브라우저 하나를 **최초 사용 시점에** 띄우고 메모이즈한다. 동시에 들어온 세션들이 같은 기동을 기다리므로 둘이 경쟁해서 두 개를 띄우는 일이 없다.
- 세션 id를 단조 증가로 바꿨다. 페이지 URL이 id를 담기 때문에, 세션이 제거된 뒤 id가 재사용되면 한 프로젝트의 파일 요청이 다른 프로젝트의 페이지로 갈 수 있다.

**`test/integration/daemon-concurrency.mjs` — 10개 통과.** 두 프로젝트를 순차로, 그리고 진짜 동시에 빌드하고, 각자 자기 마커만 담은 산출물을 받는지, 동시 실행 결과가 순차 실행 결과와 일치하는지 본다.

이빨 확인은 두 겹이다. 하나는 **수정 전후 그 자체** — 이 테스트는 고치기 전에 실패했고 고친 뒤 통과한다. 다른 하나는 `close()`가 공유 브라우저까지 닫도록 되돌려 본 것으로, 세션 하나를 제거하면 다른 세션의 페이지까지 죽어 3개가 실패한다.

## 13. 재측정 — 그리고 그 과정에서 나온 버그 세 개

§12.1 이후 §1의 근거가 통째로 무효였으므로 다시 쟀다. **재측정 자체보다 재측정을 준비하다 나온 것들이 더 컸다.**

### 13.1 벤치마크가 캐시 버그를 숨긴 것과 같은 맹점을 갖고 있었다

`bench/webcontainer.mjs`와 `bench/cache-scenarios.mjs`는 빌드 성공 여부를 **종료 코드로만** 판정했다. 그건 정확히 vite가 실행되지 못했을 때 통과하는 검사다. 두 하네스 모두 산출물이 나왔는지 한 번도 보지 않았다.

그대로 다시 쟀다면 **같은 종류의 거짓 숫자를 다시 만들어냈을 것이다.** 그래서 `bench/verify.mjs`를 추가해 두 하네스가 산출물 개수를 확인하고, 0이면 원인을 지목하며 실패하게 했다.

이빨 확인: chmod 수정을 되돌리고 벤치를 돌리니 이렇게 나왔다.

```
  boot: 1.68s   mount: 0.14s   install: 0.31s   build: 0.61s
Benchmark failed: The build exited 0 but dist/ does not exist. ...
```

부팅 1.68s, install 0.31s, build 0.61s — **빠르고 깔끔하고 완전히 가짜인** 수치다. §1에 있던 숫자가 정확히 이 모양이었다.

### 13.2 일회성 서버가 모든 인터페이스에 바인딩하고 있었다

데몬은 §5에 따라 `127.0.0.1`에만 바인딩했지만, **일회성 서버는 그런 적이 없었다.** 그런데 그 서버는 `/api/files/raw`로 **프로젝트 소스 전체**를 내보낸다. 즉 `wc-exe build`가 도는 동안 같은 네트워크의 누구나 사용자의 코드를 읽을 수 있었다. 데몬보다 오래된, 더 심각한 노출이다.

부수 효과로 포트 충돌도 감지되지 않았다. INADDR_ANY 바인딩은 다른 프로세스가 이미 `127.0.0.1:같은포트`를 잡고 있어도 성공할 수 있고, 그러면 요청이 먼저 잡은 쪽으로 간다. 실제로 이것 때문에 벤치가 60초 타임아웃으로 죽었다 — 고아 데몬이 5199를 쥐고 있었다.

### 13.3 고아 데몬 — 기록이 사라지면 관리 불능이 된다

포트를 쥐고 있던 프로세스는 이전 테스트가 남긴 데몬이었는데, `daemon status`는 "실행 중인 데몬 없음"이라고 답했다. 통합 테스트가 `finally`에서 캐시 디렉터리를 통째로 지우면서 `daemon.json`도 함께 사라졌고, 프로세스만 살아남은 것이다. **CLI로는 더 이상 멈출 수 없고 포트만 계속 점유한다.**

데몬이 유휴 검사 때 **자기 기록이 아직 자기를 가리키는지** 확인하고, 아니면 스스로 종료하게 했다.

### 13.4 `localhost` ≠ `127.0.0.1` — 캐시가 둘로 갈려 있었다

일회성 서버는 페이지를 `http://localhost:PORT`로, 데몬은 `http://127.0.0.1:PORT`로 열고 있었다. **OPFS는 origin 문자열로 갈리므로 둘은 서로 다른 저장소다.** 같은 서버에 닿는데도 캐시를 공유하지 못했고, `--cache`와 `--daemon`을 오가면 각각의 첫 실행이 매번 콜드 install을 다시 했다.

`127.0.0.1`로 통일한 효과는 컸다:

|              | 통일 전    | 통일 후        |
| ------------ | ---------- | -------------- |
| 데몬 첫 실행 | 17.68s     | **4.16s**      |
| 손익분기     | 9번째 빌드 | **2번째 빌드** |

### 13.5 실제 프로젝트에서 재려면

```bash
pnpm build
node bench/daemon.mjs ../실제-프로젝트 --runs 3
```

콜드 / 일회성 warm / 데몬 warm을 CLI 종단간으로 재고, **매 실행 산출물이 실제로 나왔는지 확인한 뒤에만** 수치를 보고한다. 절약분이 0 이하면 그렇게 말해준다.

## 14. 실제 프로젝트에서 돌려본 결과 — 숫자보다 큰 것 두 개

`bench/daemon.mjs`를 사용자의 실제 저장소들에 돌렸다. **처음 세 개가 전부 실패했고, 그 실패들이 벤치마크 숫자보다 중요했다.**

### 14.1 WebContainer 1.6.1의 mount가 비ASCII 내용을 손상시켰다

한글이 든 `package.json`이 컨테이너 안에서 깨져 `npm install`이 JSON 파싱 실패로 죽었다. 단계별로 추적했다:

| 단계                   | 결과        |
| ---------------------- | ----------- |
| 디스크                 | 정상        |
| `readProjectFileBytes` | 바이트 동일 |
| HTTP 전송              | 바이트 동일 |
| 러너가 fetch한 직후    | 바이트 동일 |
| **`mount()` 이후**     | **손상**    |

바이트 패턴이 원인을 지목했다:

```
호스트 : ec 98 b5   ec 85 98   ec 9d 84   eb 93 9c
런타임 : ec dc b5   ec 26 dc   ec 9d 1e   eb 1c 53
```

`0x98→0xDC`, `0x85→0x26`, `0x84→0x1E`, `0x93→0x1C` — **CP1252 코드포인트를 1바이트로 자른 값**이다(0x98→U+02DC, 0x85→U+2026, 0x93→U+201C). 바이트가 Windows-1252로 해석되고 있었다.

`@webcontainer/api`를 직접 찔러보니 1.6.4에서는 `Uint8Array`·문자열·`fs.writeFile` 모두 멀쩡했다. 러너만 **1.6.1**에 고정돼 있었다(`^1.3.1` 범위에 pnpm 락이 물린 상태). 1.6.4로 올려서 해결.

**픽스처가 전부 ASCII라 어떤 테스트도 이걸 잡을 수 없었다.** `test/integration/bridge.mjs`에 한글 파일 왕복 검사를 넣었다.

### 14.2 wc-exe는 `packageManager`를 무시하고 항상 `npm install`을 한다

이게 지금 가장 큰 실사용 제약이다. 사용자의 저장소 104개 중:

| 락파일              | 개수   |
| ------------------- | ------ |
| `pnpm-lock.yaml`    | **76** |
| `package-lock.json` | 8      |
| `yarn.lock`         | 2      |

**약 89%가 npm이 아니다.** wc-exe는 락파일을 무시하고 npm으로 설치하므로 의존성 트리가 로컬과 달라진다. 실제로 겪은 것:

- `github-traffic-dashboard` — `packageManager: pnpm@9.15.9`. npm이 `@libsql/client-wasm`을 끌어와 `@libsql/client/web` 해석이 그쪽으로 가고 `Missing "./web" specifier`로 빌드 실패. pnpm에서는 그 패키지가 **설치조차 되지 않는다.**
- `react-dayjs-element` — `npm install`이 `Cannot read properties of null (reading 'explain')`로 죽음.

즉 **로컬에서 잘 되는 프로젝트가 wc-exe에서는 개발자가 본 적 없는 이유로 깨진다.** 캐시 키 계산(`computeCacheKey`)은 `pnpm-lock.yaml`을 읽으면서 정작 설치는 npm으로 하는 불일치도 있다.

해결하려면 락파일을 보고 대응하는 패키지 매니저로 설치해야 한다. → **§15에서 구현했다.**

### 14.3 측정 (`ytstudio`, npm 프로젝트)

| 경로                  | 시간      |
| --------------------- | --------- |
| 콜드                  | 12.8s     |
| 일회성 `--cache` warm | 5.14s     |
| **데몬 warm**         | **2.51s** |
| 데몬 첫 실행          | 5.03s     |

**빌드당 2.63s 절약(51%), 두 번째 빌드부터 이득.** 픽스처(53%)와 일치한다. 다만 두 프로젝트 다 빌드가 가벼운 편이라, **빌드가 무거운 프로젝트에서는 여전히 다시 재봐야 한다** — 그리고 그런 프로젝트 대부분이 §14.2 때문에 아직 돌지 않는다.

## 15. 패키지 매니저 대응

### 15.1 먼저 확인한 것

인벤토리에 이름이 있는 것과 쓸 수 있는 것은 다르므로 컨테이너에서 직접 찔러봤다.

|      | 버전    | install | run |
| ---- | ------- | ------- | --- |
| npm  | 10.8.2  | ✅      | ✅  |
| pnpm | 8.15.6  | ✅      | ✅  |
| yarn | 1.22.19 | ✅      | —   |

### 15.2 선택 규칙

`src/runner/src/runtime/package-manager.ts`. 컨테이너 안에서, **마운트된 트리를 보고** 결정한다 — 실제로 설치될 트리와 판단 근거를 일치시키기 위해서다.

1. `package.json`의 **`packageManager`** — 프로젝트가 명시한 것이므로 락파일보다 우선한다.
2. **락파일** — `pnpm-lock.yaml` → `yarn.lock` → `package-lock.json` 순. pnpm으로 옮긴 저장소에 낡은 `package-lock.json`이 남아 있는 경우가 흔해서, **실제로 쓰는 매니저의 락파일**을 믿는다.
3. 기본값 **npm**.

선택 이유를 항상 로그에 남긴다. 잘못 골랐을 때 보이지 않으면 디버깅이 불가능하기 때문이다.

`--cache`의 타르볼 캐시는 npm의 cacache 포맷이고 `--cache` 플래그도 npm 것이라, **npm일 때만** 적용한다. pnpm·yarn은 `node_modules` 스냅샷만 쓴다.

### 15.3 매니저를 맞추는 것만으로는 부족했다

`github-traffic-dashboard`를 pnpm으로 설치하니 에러가 **바뀌었다** — `@libsql/client-wasm`(npm이 잘못 끌어온 것)에서 `@libsql/client`(올바른 패키지)로. 하지만 여전히 실패했다.

원인: 그 프로젝트의 락파일은 `lockfileVersion: '9.0'`인데 **컨테이너의 pnpm은 8.15.6**이다. pnpm 8은 v9 락파일을 못 읽고 **전부 새로 해석한다.** 락파일이 `vite 7.3.1`을 고정했는데 `7.3.6`이, `wrangler 4.110.0` 자리에 `4.118.0`이 설치됐다.

즉 **매니저를 맞춰도 버전이 락파일을 못 읽으면 의미가 없다.** 조용히 다른 트리를 설치한다.

`npm i -g pnpm@9`는 컨테이너에서 **EACCES로 거부된다.** 대신 `npx -y pnpm@9.15.9`가 동작하는 것을 확인했고(락파일대로 `vite 7.3.1` 설치됨), `packageManager`가 런타임과 다른 메이저를 요구하면 그 경로를 쓴다. npx는 컨테이너 수명 동안 캐시되므로 데몬 세션은 한 번만 낸다.

### 15.4 결과 — 그리고 아직 안 되는 것

| 프로젝트                   | 이전                           | 지금             |
| -------------------------- | ------------------------------ | ---------------- |
| `react-dayjs-element`      | `npm install` 내부 오류로 실패 | **성공** (pnpm)  |
| `uncharted_waters_3_map`   | —                              | **성공** (pnpm)  |
| `ytstudio`                 | 성공 (npm)                     | 성공 (npm)       |
| `rss-extensions`           | —                              | 실패             |
| `spell`                    | —                              | 실패             |
| `github-traffic-dashboard` | 실패                           | 실패 — 아래 참조 |

`github-traffic-dashboard`는 이제 **wc-exe 문제가 아니다.** `oxc-transform`이 WebContainer를 감지해 자체 wasm32-wasi 바인딩을 내려받다가 자기 폴백 경로에서 깨진다. 네이티브 의존성 계열은 §2.2에서 이미 적은 제약이다.

**전부 해결된 것은 아니다.** 실패가 남아 있고 각각 원인이 다르다. 다만 실패 이유가 "매니저를 잘못 골라서"에서 "그 프로젝트 고유의 문제"로 옮겨갔다.

## 16. 중간점검 — 대상 범주를 다시 좁히다

### 16.1 표본을 잘못 골랐었다

§14~15의 "실제 프로젝트 실패"는 **의존성 개수 순으로 고른** 저장소들이었다. 그건 이 도구의 대상 프로필과 정반대로 편향된 선택이다. 결과를 성격별로 다시 세우면 그림이 달라진다:

| 프로젝트                   | 성격                             | 결과                              |
| -------------------------- | -------------------------------- | --------------------------------- |
| `react-dayjs-element`      | 라이브러리 (`tsc && vite build`) | ✅                                |
| `uncharted_waters_3_map`   | 정적 앱 (`vite build`)           | ✅                                |
| `ytstudio`                 | 정적 HTML 앱 (`vite build`)      | ✅                                |
| `github-traffic-dashboard` | Workers + DB + 라우터            | ❌ 네이티브 의존성(oxc-transform) |
| `spell`                    | Next.js                          | ❌                                |
| `rss-extensions`           | VitePress 문서                   | ❌ 아래 참조                      |

**정적 사이트·라이브러리는 전부 성공했고, 실패는 전부 무거운 앱 프레임워크였다.** wc-exe의 대상이 전자라면 §14의 "절반이 실패" 요약은 잘못된 프레이밍이었다.

### 16.2 다만 범주 안의 실패가 하나 있었고, 그 원인은 wc-exe였다

`rss-extensions`는 VitePress 문서 사이트로 대상 범주 한복판인데 실패했다. 원인은 프레임워크가 아니라 **§15에서 추가한 npx 버전 고정 경로**였다.

```
ENOENT: no such file or directory, open '/home/.config/pnpm/config.yaml'
```

런타임에는 준비된 홈 디렉터리가 없다. npm은 자기 `/home/.npm`을 알아서 만들지만 pnpm은 부모를 만들지 않고 설정 파일을 열어서 아무 일도 하기 전에 죽는다.

고치는 과정에서 **내 수정이 두 번 헛돌았다:**

1. `XDG_CONFIG_HOME`을 넘겼는데 pnpm이 무시했다.
2. 디렉터리 생성을 `installWithCache` 안에 넣었는데, **실패하던 경로는 `--cache` 없는 `build`라 거기를 지나가지 않았다.** 그래서 "고쳤는데 아무것도 안 변한" 상태로 한 번 더 돌렸다. 지금은 두 경로가 모두 지나는 `resolvePackageManager()` 안에 있다.

fs API가 아니라 `mkdir` 명령을 쓰는 이유도 기록해 둔다 — fs API는 절대 경로도 workdir 기준으로 해석하므로(§2.2) `<workdir>/home/.config`를 조용히 만들고 증상은 똑같이 남는다.

### 16.3 남은 것은 pnpm 11 × WebContainer 비호환

디렉터리·파일을 만들어주니 ENOENT는 사라졌고 다음 벽이 나왔다:

```
[ERROR] this.db.exec is not a function
```

pnpm 11은 SQLite 기반 저장소를 쓰는데 WebContainer의 Node에 그게 없다. **wc-exe가 고칠 수 있는 문제가 아니다.** `packageManager`가 pnpm 11을 고정한 프로젝트는 현재 설치 불가다.

여기서 자동 폴백(런타임의 pnpm 8로 되돌리기)은 하지 않았다. 그건 락파일을 무시하고 **다른 트리를 조용히 설치**하는 것이고, §15가 없애려던 실패 유형과 정확히 같기 때문이다. 지금은 실패하되 이유가 드러난다.

## 17. 브릿지를 core로 정리

WebContainer를 계속 쓸지는 §18의 측정으로 정할 문제지만, **브릿지 자체는 그 결정과 무관하게 남는 자산**이다. "Node에서 WebContainer를 구동한다"는 코드는 이 CLI에 종속될 이유가 없다.

### 17.1 이미 거의 깨끗했다

의존성을 실제로 세어보니 `core/`에 CLI 의존성이 하나도 없었고 `daemon/`도 마찬가지였다. 잘못 놓인 것은 둘뿐:

- `utils/command-error.ts` — `CommandResult`를 다루는 브릿지 코드인데 CLI 유틸에 있었다 → `core/`로.
- `types.ts` — 브릿지 타입(`CommandResult`, `ServerHandlers`, `TerminalSize`, …)과 CLI 옵션(`BuildOptions`, `DevOptions`, `InstallOptions`)이 한 파일에 섞여 있었다 → `core/types.ts`와 `types.ts`로 분리.

`core/index.ts`가 브릿지의 단일 진입점이다.

### 17.2 규약이 아니라 강제로

경계를 주석으로만 적어두면 지켜지지 않는다. `core/boundary.test.ts`가 검사한다:

- `commander`·`ora`·`chalk`·`chokidar`·`http-proxy`를 import하면 실패. 이들은 "이건 라이브러리가 아니라 CLI다"를 만드는 것들이다.
- `commands/`·`daemon/`·`utils/`를 참조하면 실패. 소비자를 거꾸로 참조하는 것이므로.
- 소스 파일이 5개 미만이면 실패 — 글로브가 깨지면 나머지 검사가 **전부 공허하게 통과**하기 때문이다.

이빨 확인: `core/file-sync.ts`에 `chalk`를 넣으면 첫 번째가, `utils/spinner.js`를 넣으면 두 번째가 실제로 실패한다.

### 17.3 남은 것

패키지를 실제로 쪼개는 것(`@wc-exe/core`)은 이제 기계적인 후속 작업이다 — 경계가 코드로 강제되고 있으므로 워크스페이스 설정만 남는다. 다만 §18 측정 전에 할 이유는 없다.
