# 상주 러너(persistent runner) 설계

> `docs/virtual-filesystem.md` §10의 후속. 캐시가 install을 11.66s → 0.30s로 줄인 뒤 **부팅이 지배적 비용**이 됐다. 이 문서는 그 부팅을 반복 비용에서 제거하기 위한 설계다. 아직 **설계 단계이고 구현 전**이다.

## 1. 왜 지금 이것인가

warm 실행(캐시 히트)을 분해하면:

| 단계              | 시간      | 비고           |
| ----------------- | --------- | -------------- |
| WebContainer 부팅 | **~5.4s** | 매 실행 반복   |
| install           | 0.30s     | OPFS 캐시 히트 |
| build             | ~1.6s     |                |

부팅이 전체의 **약 70%**다. install을 11.66s에서 0.30s로 줄인 다음 남은 가장 큰 덩어리이고, **엔진 교체(§7에서 35× 느림으로 탈락)보다 훨씬 싼 개선**이다.

부수 효과도 있다: 컨테이너가 살아 있으면 `node_modules`가 메모리에 그대로 남아, OPFS에서 복원하는 0.30s조차 사라진다.

> ⚠️ 위 수치는 macOS에서 잰 것이고 프로젝트 규모에 따라 달라진다. **Phase 0(§8)에서 실제 대상 프로젝트로 먼저 확인**한 뒤 진행할 것. 부팅 비중이 작다면 이 작업 전체의 가치가 떨어진다.

## 2. 확인된 제약 — 페이지당 WebContainer 하나

`@webcontainer/api` 타입에 명시돼 있다:

> "Only a single instance of WebContainer can be booted concurrently (see `teardown`)."

여기서 구조가 강제된다:

- **세션 = 페이지 = 프로젝트.** 한 페이지는 프로젝트 하나만 담을 수 있다.
- **동시에 여러 프로젝트** → 페이지를 여러 개. 각각 부팅 비용(~5.4s)을 한 번씩 내지만, 그 다음부터는 프로젝트별로 상각된다.
- **완전 초기화** = `teardown()` 후 재부팅 = 부팅 비용을 다시 지불. 즉 "리셋은 공짜가 아니다"가 설계 전제다.
- `coep`는 **최초 부팅 때 고정**되고 재부팅으로 못 바꾼다(타입 문서). 데몬이 이 값을 프로세스 수명 동안 일관되게 유지해야 한다.
- 선택적 정리는 `fs.rm(path, {recursive})`으로 teardown 없이 가능하다.

## 3. 구조

```
wc-exe build            (짧게 살고 죽는 CLI)
   │  HTTP + 토큰, 로그는 스트리밍
   ▼
데몬 (오래 사는 프로세스)
   ├─ Hono 서버        127.0.0.1:5199 고정 (OPFS origin 안정성)
   ├─ Chromium         영속 프로파일 (~/.cache/wc-exe/chrome-profile)
   └─ 세션 N개 = 페이지 N개
        └─ 부팅된 WebContainer + 마운트된 프로젝트 + 살아있는 node_modules
```

포트 고정과 영속 프로파일은 **이미 `--cache`가 요구하던 것**이라(`src/core/cache.ts`) 새로 도입되는 제약이 아니다. 데몬은 그걸 자연스럽게 흡수한다.

## 4. 브릿지를 왜 고쳐야 하는가

지금 브릿지(`src/core/browser.ts`)는 **일회성**이다: 연산마다 `page.evaluate`로 `window.wcRunner.*`를 부르고, 로그는 puppeteer가 `console.log`를 긁어 stdout에 찍는다. 같은 프로세스가 페이지를 들고 있으니 이게 성립한다.

데몬에선 **CLI와 페이지를 들고 있는 프로세스가 다르다.** 그래서 브릿지가 이렇게 바뀌어야 한다:

|      | 지금                           | 상주 후                                |
| ---- | ------------------------------ | -------------------------------------- |
| 호출 | `page.evaluate` 일회성         | 세션 스코프 요청/응답                  |
| 로그 | puppeteer가 console 스크레이핑 | CLI로 **스트리밍**(SSE 또는 chunked)   |
| 취소 | 프로세스 죽이면 끝             | 명시적 취소 + 서버측 정리              |
| 상태 | 없음(매번 새 컨테이너)         | 세션이 상태를 **가진다** ← 위험의 근원 |

즉 이 작업의 본체는 데몬 껍데기가 아니라 **브릿지를 수명 있는 프로토콜로 올리는 것**이다.

### 제어 평면 / 러너 평면 분리

한 서버가 두 종류의 클라이언트를 받는다. 섞으면 안 된다.

- **러너 평면** — 페이지가 부른다: `/api/files`, `/api/files/raw`, `/api/dist`. Origin이 `http://localhost:5199`.
- **제어 평면** — CLI가 부른다: `/control/*`. 토큰 필요, Origin 헤더가 **있으면 거부**.

## 5. 보안 — 이게 새로 생기는 위험이다

지금 서버는 **빌드 중에만, 랜덤 포트로** 뜬다. 데몬은 **고정 포트로 항상 떠 있고 빌드를 실행**한다. 노출 성격이 다르다.

사용자가 방문한 아무 웹페이지나 `http://localhost:5199/control/build`로 POST할 수 있다는 뜻이다. 최소한 다음이 필요하다:

1. **127.0.0.1에만 바인드** (0.0.0.0 금지).
2. **베어러 토큰** — `~/.cache/wc-exe/daemon.json`에 `0600`으로 저장. 제어 평면 필수.
3. **`Origin` 헤더가 있는 제어 평면 요청은 거부** — 브라우저는 크로스오리진 POST에 Origin을 붙이고, 정상 CLI는 안 붙인다. 러너 평면은 반대로 자기 origin만 허용.
4. 데몬이 **프로젝트 경로를 검증** — CLI가 임의 경로를 넘겨 빌드시키지 못하게. (제어 평면이 이미 토큰으로 막히지만 방어 계층 하나 더.)

## 6. 진짜 어려운 부분 — 헐메틱성

지금 모델은 **매 빌드가 새 컨테이너에서 시작**한다. 상주화는 그 성질을 속도와 맞바꾼다. 이 프로젝트는 **이미 이 부류의 버그에 물린 적이 있다** — 빈 디렉터리를 캐시 HIT으로 보고해 빌드가 `vite: command not found`로 죽었던 건(§5) 상태를 잘못 신뢰한 결과였다.

그래서 무엇이 남고 무엇이 지워지는지를 **명시적으로 정의**해야 한다.

| 대상                  | 요청 간                    | 이유                       |
| --------------------- | -------------------------- | -------------------------- |
| 소스 파일             | **매번 동기화**            | 호스트가 진실의 원천       |
| `node_modules`        | **유지**                   | 이 작업의 이득 자체        |
| `dist/`               | **매번 삭제**              | 이전 산출물이 섞이면 안 됨 |
| `.npm-cache`          | 유지                       | 타르볼 캐시                |
| 그 외 컨테이너 잔여물 | 매니페스트 차집합으로 삭제 | 아래 참조                  |

### 삭제 전파 — 놓치기 쉬운 함정

`mount()`는 **추가/덮어쓰기만** 한다. 호스트에서 `src/old.ts`를 지워도 컨테이너엔 남고, 빌드가 그걸 계속 참조할 수 있다. 그러면 **호스트에 없는 파일로 빌드가 성공**하는, 가장 나쁜 종류의 거짓 성공이 된다.

따라서 동기화는 덮어쓰기가 아니라 **매니페스트 차이 계산**이어야 한다:

1. 호스트 매니페스트(경로 + mtime/해시) 수집
2. 세션이 기억하는 직전 매니페스트와 비교
3. 추가/변경 → `mount` 또는 `writeFile`
4. **삭제된 경로 → `fs.rm`**
5. 새 매니페스트를 세션에 저장

### 리셋 트리거 (teardown + 재부팅)

- lockfile 변경 → 사실은 캐시 키가 이미 처리하므로 리셋까지는 불필요. install만 다시.
- **wc-exe 버전 변경** → 러너 번들이 바뀌었으므로 리셋 필수
- `--fresh` 명시
- 세션이 오류 상태(이전 요청이 예외로 끝남)
- 유휴 만료

## 7. 수명 주기

- **자동 시작** — 첫 CLI 호출이 데몬을 detached로 띄운다. 사용자가 따로 켤 필요 없음.
- **디스커버리** — `~/.cache/wc-exe/daemon.json`에 `{pid, port, token, version, startedAt}`.
- **헬스체크** — `GET /control/health` → 버전·업타임·세션 목록.
- **버전 불일치** — CLI가 자기 버전과 데몬 버전을 비교해 다르면 **죽이고 재시작**. 이게 없으면 업그레이드 후에도 낡은 러너가 계속 돈다(실제로 겪기 쉬운 함정).
- **유휴 종료** — 기본 10분 무요청 시 종료. 메모리를 무한정 붙들지 않기 위함.
- **크래시 복구** — CLI가 연결 실패하면 stale `daemon.json`을 지우고 재시작.
- **수동 제어** — `wc-exe daemon status|stop|restart`.

## 8. 단계별 진행 — 각 단계가 독립적으로 값을 낸다

**Phase 0 — 전제 검증 (측정만, 코드 없음)**
실제 대상 프로젝트에서 `bench/webcontainer.mjs`로 boot/mount/install/build 비중을 잰다. 부팅이 실제로 지배적인지 확인. **아니면 여기서 중단한다.**

**Phase 1 — 브릿지를 세션 프로토콜로 (데몬 없음)**
`wcRunner`를 세션 개념 위로 올리고, 로그 스트리밍과 매니페스트 차이 동기화를 도입한다. 동작은 지금과 동일하게 유지(여전히 한 번 쓰고 버림). **위험이 낮고 그 자체로 유용**하며, 삭제 전파는 지금 모델에서도 옳은 개선이다.

**Phase 2 — 데몬**
제어 평면 + 토큰 + 수명 주기 + `--daemon` 옵트인. 기본은 꺼둔다.

**Phase 3 — 헐메틱성 하네스, 그 다음 기본값 전환**
아래 검증이 통과해야 기본값을 켠다.

## 9. 어떻게 "맞다"고 증명할 것인가

속도만 재면 안 된다. 이 변경의 위험은 **틀린 산출물**이므로:

1. **바이트 동일성**: 같은 프로젝트를 (a) 일회성 (b) 데몬 재사용 두 경로로 빌드해 `dist/`를 바이트 비교. **다르면 버그.**
2. **삭제 전파**: 파일을 지우고 재빌드 → 컨테이너에서도 사라지고 빌드가 그걸 참조하지 않는지.
3. **반복 안정성**: 같은 세션에서 N회 연속 빌드 → 매번 동일 산출물(누적 오염 없음).
4. **검사의 실효성**: 위 검사들이 **일부러 깨뜨렸을 때 실패하는지** 확인. (§10 방법론 — 통과만 보면 검사가 비어 있어도 모른다.)

## 10. 아직 모르는 것 (측정으로 답할 것)

- 대형 프로젝트에서 **매니페스트 차이 동기화 비용**. 이게 부팅 절약분을 갉아먹으면 이득이 준다.
- 오래 산 WebContainer가 **빌드 반복 시 메모리 누수**를 내는가. 유휴 종료가 완화책이지만 한계 확인 필요.
- **teardown + 재부팅 vs 새 페이지** 중 리셋이 어느 쪽이 싼가.
- 페이지(=세션) 여러 개를 동시에 띄웠을 때 Chromium 메모리 상한.

## 11. 기대 이득 (미검증)

warm 실행이 `5.4(부팅) + 0.3(install) + 1.6(build) ≈ 7.3s`에서 **`동기화 + 1.6(build) ≈ 2s 내외`**로 줄어드는 것이 목표다. 부팅과 캐시 복원이 모두 빠지기 때문이다.

**단, 이 수치는 아직 측정된 적 없다.** Phase 0과 Phase 3의 실측이 나오기 전까지는 가설로만 다룰 것.
